## §2 Constraints carried in from the record — binding

- **The D17/D18 masking constraint.** Satisfied by construction here (the corpus search replaces the window and the matcher in one move), but binding if scope ever shrinks: **no matcher-only intermediate ships.**
- **Matching semantics go in the tool description** — the rule measured into `fulltext/07-search.md`: descriptions shape input; D17's root harm was matching semantics the caller was never told.
- **Three zeros, never one string.** "No match in the corpus," "no match in the fallback window," and "the search errored" are three different responses. A `/search` failure must surface as the §9 envelope or the labeled fallback — never as an empty result set. This is the scan-that-errors rule bound onto the tool itself.

- **#65 coherence:** `results_count` equals the length of the typed list it counts, in every response shape including the fallback.
- **Quota:** GovInfo's 36,000/hr bucket is **shared with bill-text content fetches** (M3-confirmed: one request per search call, one counter across `/search` and `/packages`). Deployment reality recorded 2026-08-24 (maintainer): **single-user stdio is the designed mode — the license prohibits SaaS hosting** — so per-call cost is negligible; what survives of this constraint is only that bulk search loops must not starve retrieval.

## §2a Upstream interface — per published documentation, 2026-08-24 (probe confirmation owed)

Sources, maintainer-supplied 2026-08-24: `govinfo.gov/features/search-service-overview` (service), `govinfo.gov/help/search-operators` (query language), `govinfo.gov/help/bills` (BILLS fields). The service is labeled **public preview** (launched 2023-08-15) — a stability caveat worth one line in the completion report when this ships.

- **Endpoint:** POST `https://api.govinfo.gov/search`. Requires an API key (`DEMO_KEY` exists for low-volume probing).
- **Request:** `query` (string, the full query language below), `pageSize` (max 1000), `offsetMark` (**cursor**: `*` on the first call, then the value the previous response returned), `sorts` (array of `{field, sortOrder}`; fields `score`/`publishdate`/`title`/`lastModified`; "sorting by score ascending is not supported"), `resultLevel` (`"package"` or `"default"` — default is a mix of granules and packages), `historical` (bool, default false, "include non-current documents").
- **Response:** `count` (total matches) plus records carrying `title`, `packageId`, `granuleId`, `lastModified`, `governmentAuthor`, `dateIssued`, `collectionCode`, `resultLink`, `dateIngested`, and a `download` link object.
- **Query language:** multiple words are an **implied AND** (documented verbatim: "spaces between words are treated as an implied 'and'"); `"quoted phrases"` match adjacent-and-in-order; `AND`/`OR`/`NOT`/`-` booleans; `?`/`*` wildcards; `adj`, `before/#`, `near/#` proximity; `field:value` fielded terms (no spaces around the colon); `field:range(a,b)` ranges. Quotes inside the JSON `query` are backslash-escaped.
- **BILLS fields:** `collection:bills`, `congress:`, `billtype:` (`hr s hjres sjres hconres sconres hres sres`), `docnumber:`, `billversion:`, `title:`, `shorttitle:`, `chamber:`, `member:`, `memberparty:`, `memberstate:`, `committee:`, `actiondate:`, `publishdate:`, `isprivate:`, `isappropriation:`, `uscodecitation:`, `statutecitation:`, `plawcitation:`. Package ids follow `BILLS-{congress}{billtype}{docnumber}{billversion}`.
- **Noted, out of scope here:** `uscodecitation:`/`plawcitation:`/`statutecitation:` are an upstream affordance adjacent to the `amends` work (F36's citation classes, queryable corpus-wide). Recorded so it is not rediscovered; not part of this fix.

**What the documentation changes:** implied-AND semantics are the *opposite* of D17's OR-substring pathology, so the upstream default is already the correct matcher; the design work is mostly honesty plumbing and pagination. The load-bearing unknowns left for probes: tokenization of punctuated terms (`St.` in A1's query), what `historical` means for bill *versions* (it may do Q3's dedup upstream), granule-vs-package behavior for BILLS under each `resultLevel`, and cursor stability.

## §2b Measured behavior — probe run 2026-08-24 (`runs/govinfo-search/2026-08-24T234232Z/`)

29 keyed calls against the live endpoint by this session (maintainer-supplied key; probe script archived in the run dir; the key appears in no artifact — grep-verified before commit). Every §3 prediction was exercised; three documented-or-assumed behaviors were falsified, and per the preregistration those are findings recorded here.

**Confirmed:**

- **Implied AND, exactly as documented.** The full unquoted A1 title → `count: 1`, exactly `BILLS-119hr4631ih`. The dot-stripped `St Louis` variant is identical — unquoted tokenization forgives punctuation.
- **A2/A3/A4 as predicted:** 31 / 31 / 0. The D17 differential is structurally dead — adding or dropping `Act` changes nothing, and the 31 are RECA bills, not a newest-bills page.
- **`RECA` keyword → 6 hits including both `119hr4631ih` and `119hr10115ih`** — A8's real-use case is reachable upstream.
- **Fielded `congress:`/`billtype:`/`docnumber:` returns exactly the bill's version set** — S. 1071 → all four versions (`is`/`es`/`enr`/`eah`). The version-discovery affordance is live, for free.
- **Cursor pagination is sound:** pages disjoint, and reusing a 90-second-old `offsetMark` reproduces page 2 identically — cursors are stable and replayable, which is what Q4's page-token option needs. **An exhausted page still returns a non-null `offsetMark`** (the `count: 1` probe carried one; only the zero-hit query returned null — adjudicated from the same run's artifacts, 2026-08-24), so end-of-results must be **computed** from records-consumed vs `count`, never inferred from cursor nullness.
- **Shared quota bucket confirmed:** a `/packages` summary call decremented the same `X-RateLimit-Remaining` counter as `/search` (limit 36,000); one request per search call.
- BILLS records are package-level regardless of `resultLevel` (`granuleId: null`), and `historical` true/false are identical on S. 1071 — both knobs are no-ops for this collection.

**Falsified / surprises — all load-bearing:**

1. **Quoted phrases miss bills whose *titles* carry the phrase.** `"St. Louis RECA Readjustment Act"` → 0 while the same words unquoted → 1; `"RECA Readjustment Act"` → 0; `"Readjustment Act"` → 2 hits *not* including hr4631. Yet `"Radiation Exposure Compensation Act"` → 4 (body-text occurrences), and fielded `shorttitle:"St. Louis RECA Readjustment Act"` → 1 exact. The mechanism is uncharacterized (title text under phrase-adjacency indexing); the operational rule does not depend on it: **phrase queries are unreliable against title text — plain AND terms, or `title:`/`shorttitle:` fields, are the reliable forms.**
2. **The default sort is not relevance.** No-`sorts` ordering differs from explicit `score DESC` and looks package-id-shaped; the explicit ordering is visibly relevance-like (the two RECA bills lead). The docs never actually stated a default — the assumption was ours.
3. **Malformed requests wear the outage shape.** Bad `offsetMark`, bad `sorts`, non-numeric `congress:`, and a ~900-term query all return the same generic 500 (`"Oops, Something went wrong…"`) — indistinguishable from GovInfo-down at the HTTP level.
4. **An empty query matches the entire corpus** — `count: 8,759,900`, cross-collection, granule-level records, HTTP 200.

## §4 Open design questions

Routing per `documentation/CLAUDE.md`: **RULE HERE** = IR/technical judgment, decided in this file with rationale; **MAINTAINER** = requirements/product. Gating measurements marked.

- **Q1 — surface.** Same `search_bills` operation, signature-preserved, is the presumption (the mandate names the tool). MAINTAINER only if a parameter must break — **Q4 now invokes exactly this carve-out.**
- **Q2 — query semantics. RULED 2026-08-24 on §2b.** **Pass the caller's `keywords` through to `query` unmodified**, server appending the scoping terms (`collection:bills`, `congress:{n}` when set) and always appending explicit `sorts` (Q9). **Blank or whitespace-only `keywords` are rejected client-side with an `invalid_parameters` envelope, never sent** — an empty upstream query matches 8.76 M documents (§2b item 4). No silent rewriting; the JSON transport escape is the only server-side transformation. The tool description states the measured semantics: words are ANDed; **do not quote bill names — quoted phrases are measured to miss title text** (§2b item 1); `title:"…"`/`shorttitle:"…"` are the exact-title forms and pass through; `OR`/`NOT` available. *Deferred option, recorded not built:* disclosed server-side augmentation `(<kw>) OR shorttitle:"<kw>"` could rescue phrase-shaped intent, but unquoted AND already resolved every measured case at `count: 1` — simplicity holds until a real miss is observed.
- **Q3 — version multiplicity. RULED 2026-08-24 on §2b: dedup is client-side** — `historical` is measured a no-op for BILLS and the multiplicity is real (S. 1071 → four records). Group result records by `(congress, billtype, docnumber)` parsed from `packageId` (`fulltext/00-INDEX.md`: carry the authoritative value — the id is in hand, do not re-derive from other fields); front the most authoritative version per `fulltext/03-data-sources.md` §3 precedence; **carry the full per-bill version list in the hit** — the records are already in hand, the affordance is free. **Version discovery: RULED partial discharge (maintainer, 2026-08-24)** — search hits become the affirmative version-discovery surface, `version_not_available` keeps covering the pinned-version error case, and the tool description must teach the affirmative path explicitly. **One precision correction folded in by this session, same day: a keyword hit carries only the versions whose *text matched* the query — the field is named `matched_versions` so it cannot be misread as the complete set.** The complete set is available through the same tool by disclosed usage: a fielded `congress:{n} billtype:{t} docnumber:{m}` query with no text terms returns exactly the bill's versions (measured, S. 1071 → 4/4, §2b) — so the maintainer's floated versions-only query is already reachable via pass-through, the description teaches the form (§6.5), and a dedicated mode is **deferred, gated on an observed consumer stumble** over the extraneous-results shape.

- **Q4 — pagination surface. RESHAPED by §2a: upstream is a cursor (`offsetMark`), not an offset — random access does not exist.** D18 already established the shipped `offset` is incoherent (it pages the candidate window), so no consumer can be depending on correct offset behavior. Options: (a) replace `offset` with an opaque page-token parameter mirroring the cursor — honest, cheap, **breaking**; (b) keep `offset` and emulate by walking cursors server-side — non-breaking, cost linear in offset, and it re-manufactures random-access semantics upstream doesn't offer; (c) drop pagination and cap results. **Recommendation: (a)** — the parameter is broken today, so the break is nominal and the honesty is real. §2b adds the supporting evidence: cursors are stable and replayable at ≥90 s with disjoint pages, so an opaque token is a faithful wrapper, not a leaky one. **SETTLED (maintainer, 2026-08-24): option (a).** The signature change is approved as the honest path given that random access does not exist upstream; emulating it was rejected as expensive and purposeless. Contract in §6.3.
- **Q5 — filter composition** *(gated M1)*. `congress` and bill type map to fielded terms (`congress:`, `billtype:`) — upstream, settled. **Policy area has no GovInfo field** (§2a's list is exhaustive per the docs): options are dropping the filter for the corpus path, post-filtering the corpus result set (unlike D18's shape this filters *matches*, not a recency page — but it breaks `count` honesty and pagination), or keeping it fallback-only. **SETTLED (maintainer, 2026-08-24): dropped from the corpus path — and since a filter that binds only in fallback mode is a trap, the parameter leaves `search_bills` entirely (§6.1).** *Deferred idea, recorded so it is not rediscovered:* a congress.gov-backed policy-area search as a separate tool, limitations disclosed — out of scope for this fix.

- **Q6 — response shape.** Keep the existing `search_bills` response model; add source disclosure — a machine-readable marker distinguishing corpus results from fallback-window results, plus the D17/D18 honesty metadata (`bills_scanned`, oldest `updateDate`, `window_truncated`) whenever the fallback fires. Corpus responses carry upstream `count` (total matches) beside the returned page so a truncated list is legible. #65 coherence binds: `results_count` counts the returned list, not upstream `count`. **RULED, maintainer concurring 2026-08-24; the response metadata is a mandatory tool-description item (§6.5) so the consumer knows what it is reading.** Contract in §6.2.

- **Q7 — fallback trigger. RULED 2026-08-24 on §2b item 3, which reshaped it: a 500 cannot be read as "GovInfo down" — it is also what a malformed request returns, with an identical body.** (i) **Strict construction:** the only unvalidated content in `query` is the caller's keywords; every server-built term (`sorts`, `pageSize`, `offsetMark`, scoping) is validated before send, so a 500 implicates the endpoint or the caller's own syntax, never our plumbing. (ii) **Trigger classes, all labeled in the fallback metadata:** HTTP 500 → fallback fires as `govinfo_search_error`, remediation naming the ambiguity ("the query may use unsupported syntax, or the search service is failing — simplify the query to plain words to distinguish"); network unreachable/timeout → fallback as `govinfo_unreachable`; 429 → fallback as `govinfo_rate_limited`; keyless → **no fallback**, `api_key_missing` envelope per F31 (the operator must act). **Amended 2026-08-24 (maintainer): the canary is ruled IN, reversing the deferral above.** Rationale accepted and recorded: the server's designed deployment is **single-user stdio — the license prohibits SaaS hosting** — and a search costs one call against a 36,000/hr bucket, so a canary is near-free and buys real diagnosability. Corroborating instance, independently observed by the maintainer: a nonexistent operator typed into GovInfo's own swagger UI produced the same unhelpful generic 500 (§2b item 3's shape, from a third instrument). The canary changes the 500 branch: canary succeeds → the caller's input is implicated → **no fallback**, a `govinfo_query_error` envelope (remediation: plain words, no operators; when a `page_token` was supplied, it is named as the other suspect); canary fails → outage confirmed → fallback as `govinfo_search_error`. Normative flow table in §6.4.

- **Q8 — cache composition.** Presumption recorded in §1: the hit carries package/version identifiers (upstream `packageId` decomposes per §2a's id structure); no prefetch (quota). **SETTLED (maintainer, 2026-08-24): no speculative prefetch.** The confirming rationale is recorded: which hits would even warrant it — the top hit? all of them? — a page of never-consulted bills would evict genuinely warm entries from the cache's 500 MB LRU. The hit carries the identifiers; warming happens when the consumer actually calls `search_bill_text`.

- **Q9 — ranking. RULED 2026-08-24, and §2b item 2 upgraded it from preference to necessity: the upstream default is NOT relevance** (no-`sorts` ordering is package-id-shaped). **Every request sends explicit `sorts: [{score, DESC}]`.** No caller-facing sort parameter (the fallback window is already recency-shaped); revisit only on a real request.
- **Q10 — time-bounding. RULED 2026-08-25 (maintainer directive reversing part of the §6.1 removals, + M5 measurements).** The maintainer's call: time-bounding is supported upstream and was advertised surface — support it. **`fromDateTime`/`toDateTime` are restored, mapped to `publishdate:range(from,to)` on the corpus path.** M5 measured every mapping property against known-date bills (run `runs/govinfo-search/*-m5/`, 7 probes, all preregistered predictions held): range **inclusive both ends** (single-day range returns the exact-date bill), **both one-sided forms native** (`range(from,)` and `range(,to)` both correct), year form `publishdate:2026` works, and a datetime string inside a range is tolerated upstream. Ruling details: inputs validated client-side as ISO date or datetime, **datetime truncated to date** before assembly (tolerated upstream, but the canonical query keeps the description honest), `from ≤ to` enforced, one-sided passes through natively; **semantic shift disclosed** — the corpus path bounds the *version document's publication date* (`dateIssued`), not congress.gov's `updateDate`, and a bill matches when any text-matching version falls in range; **the fallback applies the same bounds client-side over the window rows' `updateDate`** (the nearest available field), with the difference named in the fallback message. `format` stays removed (ratified — an output-shape artifact with no corpus meaning); `sort` stays removed per Q9.
- **Q11 — local snippets (RULED 2026-08-25; maintainer-approved direction, consumer-proposed; NOT in the reopened PR — next batch).** Upstream has no snippets (§8 measured), but this server owns the *other* index: for a hit whose bill is retrievable locally, run the caller's terms against the FTS5 segments and attach tool-generated match contexts as a triage snippet. Two composable modes, both maintainer-named: **(a) opportunistic, always on, cache-only** — a hit whose package is already in the persistent cache gets a snippet for free, no network; **(b) opt-in bounded fetch** — an explicit request parameter (`snippet_fetch: N`, hard cap small, e.g. ≤ 5) additionally downloads-and-parses the top-N uncached hits, spending real cost only on caller demand (consistent with Q8: this is requested warming, not speculation — and it leaves those bills warm for the follow-up reads a research session makes anyway). **Binding disambiguation contract (the make-or-break, and the three-zeros rule again):** the snippet field is tri-state and the states must be structurally distinct — a snippet; `snippet: null` + a marker meaning *upstream match not localized* (the semantics mismatch is real: GovInfo ANDs raw words, FTS5 matches stemmed phrases, so a genuine upstream hit can fail local localization — localize per-term, not as a phrase, to narrow the gap); and absent-because-not-attempted (uncached, no opt-in). An empty string masquerading as "no match" recreates exactly the silent-zero ambiguity this tool exists to kill; if the tri-state cannot be kept clean, the feature does not ship.
- **Q12 — starved-result diagnostics (deferred, refined 2026-08-25):** per-term document-frequency probes on low-count results, surfacing as a **structured field** (not prose), firing **only for multi-term queries** (a one-term zero needs no explanation and is where the extra calls would be wasted). Cost: one cheap call per term, near-free under the Q7 deployment reality. Maintainer's call on scheduling; not in the reopened PR.

## §6 Tool contract — the design (2026-08-24, written with every question settled)

Normative for the implementation. Parameters are named by role — retained parameters keep their shipped names, and this session does not read implementation source, so the mapping onto the existing module layout is the implementer's.

### §6.1 Request

- `keywords` — required. Stripped; blank → `invalid_parameters` envelope, never sent upstream (Q2). Otherwise passed through verbatim into `query`.
- `congress` — optional; validated as a positive integer **here** (a non-numeric value 500s upstream, §2b) → appends `congress:{n}`.
- The bill-type parameter (if the shipped tool carries one) — validated against the eight documented values → appends `billtype:{t}`.
- `limit` — output cap in **bills**; existing clamp discipline applies (out-of-range clamps with the shared validator's advisory wording).
- `page_token` — optional; **replaces `offset`** (Q4). Opaque; contents §6.3. A malformed or expired token surfaces through the 500→canary path (§6.4), whose remediation names the token.
- The policy-area parameter is **removed** (Q5). *Corrected 2026-08-25 at implementation: the ruling was vacuous as written — no policy-area **parameter** existed; it was matcher behavior inside the window filter, retained in the fallback (the check-dead-defensive rule, missed by this session). What actually left the surface: `offset` (Q4), `sort` (covered by Q9's no-sort ruling), and `format`/`fromDateTime`/`toDateTime` — window-tool artifacts removed on implementation initiative.* **Ratification landed 2026-08-25 (Q10): `format` removal ratified; `fromDateTime`/`toDateTime` RESTORED** — validated ISO date/datetime (datetime truncated to date, `from ≤ to`), assembled as `publishdate:range(from,to)` with native one-sided forms; fallback path filters `updateDate` client-side with the semantic difference named. Measured mapping properties at Q10.
- Assembled upstream request: `query = "{keywords} collection:bills[ congress:{n}][ billtype:{t}]"`; `sorts: [{"field": "score", "sortOrder": "DESC"}]` always (Q9); `pageSize` per §6.3; `offsetMark` from the token, else `*`; `resultLevel` and `historical` **omitted** — measured no-ops for BILLS (§2b); nothing is sent that does nothing.

### §6.2 Response

- Hits are **bills**, deduped from upstream version-package records in rank order (first occurrence wins), grouped on `(congress, billtype, docnumber)` **parsed from `packageId`** — the carry-don't-reconstruct rule binds: the id is authoritative, nothing is re-derived from other fields.
- Each hit carries: the bill identity; the **fronted version** — most authoritative per `fulltext/03-data-sources.md` §3 precedence *among this bill's fetched records* — with its `packageId`, `title`, `dateIssued`; and **`matched_versions`** — every version of this bill present in the fetched records, precedence-ordered. Named `matched_versions`, not `versions`: a keyword query returns only versions whose text matched, so the list is match-scoped by construction; the complete set comes from the fielded no-text query (§6.5 item 3).
- `results_count` = length of the returned hit list (#65).
- `total_version_matches` = upstream `count`, named for its real granularity: it counts version packages and can exceed the number of distinct bills; the description says so (Q6).
- `search_source`: `"govinfo_fulltext"` or `"recency_window_fallback"`; fallback responses additionally carry the trigger class (§6.4) and the window honesty metadata (`bills_scanned`, oldest `updateDate` in the window, `window_truncated`).
- `next_page_token`: present while unconsumed upstream records remain; `null` when exhausted. Exhaustion is **computed** — `records_consumed ≥ count` — never inferred from cursor nullness (§2b: an exhausted page still returns a cursor; only a zero-hit query returns null).

### §6.3 Pagination and dedup mechanics

- The token is server-encoded and opaque to the caller: `{offsetMark, records_consumed}`. `records_consumed` accumulates upstream records across the walk and is the exhaustion numerator against `count`. **Amended 2026-08-25 — implementation-found, RATIFIED: the token carries a third component, `skip`.** As originally written, whole-page consumption plus the `limit` cap **loses bills** whenever a page dedups to *more* than `limit` bills (a 3×limit page of single-version bills dedups to 3×limit; A6 forbids exactly this loss). Spec-caused — the F33 family: a ruling correct on the shape it was written against (dedup *shrinkage*) and wrong on the adjacent one (dedup *overshoot*). `skip` resumes intra-page on the measured-replayable cursor; `skip = 0` degenerates to the two-field shape, and the resume boundary stays inside the one tolerated same-identity duplication class. Failing shape pinned in `test_overshoot_page_consumes_only_selected_bills_records`; lossless walk in `test_full_walk_over_one_page_is_lossless_and_disjoint`.
- **One upstream fetch per tool call** — predictable cost, one request. `pageSize = min(3 × limit, 300)`: the overfetch absorbs dedup shrinkage (most bills carry 1–4 versions).
- **Short pages are legal:** when a version-heavy page dedups below `limit`, the call returns what it has with `next_page_token` set. Disclosed in the description (§6.5).
- **The one tolerated duplication class:** a bill whose version records straddle an upstream page boundary reappears on the next page (per-call dedup holds no cross-call state). Overfetch makes it rare; the description discloses it; both appearances carry the same bill identity, so a consumer dedups by id trivially. A6's acceptance treats this class as the only passable duplication.
- A5's monotonicity holds by construction — identical upstream ranking, rank-order dedup, constant overfetch factor — and is still measured at acceptance, not assumed.

### §6.4 Failure flow (Q7 as amended — canary in)

| main-call outcome | action | response |
|---|---|---|
| 200 | — | normal corpus response |
| 500 | **canary:** one server-built constant query, known valid, zero caller input | canary 200 → **no fallback** — `govinfo_query_error` envelope (caller's input implicated; remediation: plain words, no operators; names the `page_token` as the other suspect when one was supplied). canary non-200 → outage confirmed → fallback as `govinfo_search_error` |
| network unreachable / timeout | no canary | fallback as `govinfo_unreachable` |
| 429 | no canary (it would spend quota to confirm quota) | fallback as `govinfo_rate_limited` |
| no key configured | — | `api_key_missing` envelope per F31; **no fallback** |

Every fallback response is the #66 honest window wearing `search_source: "recency_window_fallback"`, its trigger class, and the window metadata — the §2 three-zeros rule discharged by structure, not prose.

**Row added 2026-08-25 — ratified from the A7 artifact (the shape was unspecified; the shipped behavior exceeded the spec and got it right): both legs down.** When the corpus call fails *and* the fallback fetch itself fails, the tool returns a §9 envelope — the primary trigger code at top level (`govinfo_unreachable` in the observed instance), a message naming **both** failures, the fallback's own error nested in `detail`, retry remediation. Never an empty success — the three-zeros rule's fourth shape. *Nit, non-blocking: the observed nested `fallback_error` is a stringified envelope; prefer a structured object when next touched.*

### §6.5 Tool description — mandatory content

The description is load-bearing (§2). The implementer words it; every item below must be present:

1. What the corpus is: full text of congressional bills, all versions, searched at GovInfo.
2. Matching semantics — **normative text adopted verbatim 2026-08-25** (consumer-drafted, maintainer-approved; **the one item shipping in the reopened PR**). The docstring's matching-semantics bullet becomes:

   > Matching semantics: words are ANDed -- every term must appear in the SAME document, so each added word strictly shrinks the result set and can never grow it. Start with the distinctive minimum: the fewest words that name the thing, and add terms only to cut a set that came back too large. Do NOT add words describing the topic, category, or what the bill does -- that is the natural way to phrase a search and the usual cause of a starved result. Worked example: "Radiation Exposure Compensation Act amendments downwinders" returns 1 bill; dropping the two description words returns 26, including the enacted vehicle. A small count means the terms rarely co-occur, NOT that few such bills exist -- re-query narrower before concluding anything. Synonyms do NOT broaden here: unlike search_bill_text, which ORs its queries array and rewards adding alternate phrasings, an added synonym on this path intersects and discards.

   The no-quoted-bill-names warning, `title:`/`shorttitle:` forms, and operator pass-through stay alongside it. Three properties are deliberate and survive any rewording: the **worked example with magnitudes** (the abstract AND statement was already in the docstring, was read, and was ignored — 26→1 is what stops the behavior), the **starvation clause** (the damage is a small count treated as a finding — the `recency_window_fallback` principle on a different failure path), and the **cross-tool boundary line** (`search_bill_text` ORs its queries and rewards synonyms; this tool intersects and discards; the habit carries across two adjacent tools and nothing else marks the boundary — warning placed only on the silent-failure side, deliberately no reciprocal pointer).
3. **Version discovery:** hits carry `matched_versions`; for a specific bill's *complete* version set, query `congress:{n} billtype:{t} docnumber:{m}` with no text terms (measured: returns exactly the version set). This is the affirmative discovery path (Q3 ruling); `version_not_available` remains the pinned-version error's disclosure.
4. Count semantics: `total_version_matches` counts version packages; `results_count` counts returned bills.
5. Pagination: pass `next_page_token` back verbatim; pages can run short; a bill can rarely reappear across pages (same id).
6. Fallback: when `search_source` is `"recency_window_fallback"`, results are the most-recently-updated window, not the corpus — read the trigger class.
7. Blank `keywords` are rejected.
8. Time-bounding: `fromDateTime`/`toDateTime` bound the **version's publication date** on the corpus path (inclusive; either side optional) — not congress.gov's update date; in fallback mode they bound `updateDate` over the window instead, and the response says so.
